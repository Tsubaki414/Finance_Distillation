* MVP

## 二、下一轮的唯一目标

完成一个真实可运行的 Vertical Slice：

> 真实 KOL 推文采集 → 内容清洗 → 知识/语言/习惯画像 → 多 donor persona 组合 → 基于真实新事件生成差异化内容 → 来源与评估 → 前端展示。

这次重点是纵向做深，不是继续横向扩展架构。

不要再用“33 个来源登记”“41 项需求映射”“若干静态页面”作为主要完成度指标。完成度必须由实际语料数量、实际运行结果和可复现评估决定。

## 三、先读取真实推文，API 成功次数不是目标

不要把 API call 数量本身当 KPI，但 3 个账号、单页 timeline 明显不足。

### 试点数据目标

优先从现有金融 KOL 名单和 source registry 中选择 12 个具有真实内容价值的 donor：

* 中文 donor 至少 6 个。
* 英文 donor 至少 6 个。
* 尽量覆盖三个母领域：

  * 宏观与数据流
  * 个股与产业链
  * 交易体系与市场心理

对每个 donor：

* 获取最近 180 天，或最多 500 条 timeline items。
* 保留原始时间顺序。
* 包含原创、reply、quote、repost 等关系信息。
* 目标是清洗后至少保留 150 条真正由该作者产生的金融相关内容。
* 若某账号无法达到 150 条，应标记数据不足并替换 donor，不能用重复或广告补足。
* 总体目标至少形成约 1,800 条可用金融内容。
* 如果 API 套餐、字段或历史深度使这个目标无法实现，先给出精确的调用数量、套餐限制、预计成本和替代路径。

不要未经允许购买套餐或扩大计费。但也不能只做 6 次连通测试后停止：

1. 先检查现有套餐额度和分页机制。
2. 计算完成试点所需的预计请求数。
3. 在现有已授权额度内尽可能执行。
4. 如果确实需要新增付费，只询问具体预算选择，不要退回继续写架构。
5. 可以评估官方 API、RSS、公开页面、用户导入和其他合规渠道作为补充。
6. 不得打印或暴露密钥。

## 四、逐条清洗并证明系统真的看过推文

对原始 timeline item 至少分类为：

* 原创金融分析
* 原创非金融内容
* 新闻转述
* 原始研究或数据引用
* 回复
* 引用评论
* 纯转推
* 广告或带货
* 项目推广
* 生活内容
* 喊单但无分析
* 可能由他人代写或来源不明
* 无法判断

要求：

* 保留分类置信度。
* 保留被排除原因。
* 随机抽取至少 300 条，由人工或严格规则复核。
* 统计每个账号的金融相关率、原创率、广告率、回复率和来源引用率。
* 展示具体推文 URL 和分类结果。
* 不允许只让 LLM 输出一个笼统人物总结。
* 整理版 Markdown、OCR 摘录和别人转述不能被当作作者原始语言样本。

## 五、实际建立三层 donor 画像

### 1. Knowledge Profile

基于真实金融推文提取：

* 主要研究领域
* 高频公司、资产和行业
* 常用信息来源
* 核心分析框架
* 主要因果机制
* 时间周期
* 对风险的理解
* 反复出现的观点
* 观点随时间的变化
* 已被证实或证伪的判断
* 明确知识边界
* 不能迁移进 persona 的广告、收益宣传或无依据结论

每项特征必须绑定若干原始 post IDs，而不是仅写模型总结。

### 2. Style Profile

至少量化：

* 句长分布
* 段落长度
* 单帖字符或 token 分布
* 数字密度
* ticker 密度
* 外部链接密度
* 图表和图片使用比例
* 设问频率
* 第一人称比例
* 确定性与 hedge 词频
* 术语解释位置
* 先结论还是先证据
* 列表、碎片句和长论证比例
* 引用别人观点的方式
* 开头和结尾结构
* 高频词与禁用迁移词

不能把单一口癖、脏话或错别字当作风格的主要证明。

### 3. Content Habit Profile

基于完整时间序列和元数据分析：

* 原创、回复、引用和转推比例
* 发文间隔分布
* 内容爆发与沉默时段
* 工作日和周末差异
* 不同主题下的内容长度
* 对财报、宏观数据和市场异动的反应时差
* 是否会更新旧观点
* 是否会承认错误
* 哪类事件只简短评论
* 哪类事件会形成长线程
* 主题切换规律
* 某些结论无法观察时必须标记 unknown

注意：这是内容习惯画像，不要求实现自动发布。

## 六、这次必须有真实 ML，而不只是 LLM Prompt

不要求为了“看起来高级”训练大模型，但必须完成真实、可复现、带指标的 ML 实验。

### 实验 A：金融相关内容分类

* 建立人工复核样本。
* 至少比较：

  * 规则 baseline
  * embedding 或传统文本分类 baseline
  * LLM 分类
* 报告 precision、recall、F1 和典型失败案例。
* 如果样本不足，明确置信区间和限制。

### 实验 B：作者与风格可辨识性

* 使用 stylometric features 和文本 embedding。
* 训练一个轻量作者归属分类器。
* 按时间划分训练集和测试集，不能随机把同一 thread 拆进两边。
* 报告真实作者归属准确率或 macro-F1。
* 展示最有区分力的特征。
* 如果真人作者本身无法被可靠区分，应据此调整 persona 设计。

### 实验 C：主题聚类与知识差异

* 对清洗后的金融内容进行 embedding 和聚类。
* 展示不同 donor 的主题分布。
* 识别哪些 donor 实际在重复同一上游来源。
* 识别真正互补的 donor。
* 不要因为账号名字不同就假设知识不同。

### 实验 D：Persona 生成消融

至少比较：

1. 基础模型，无 persona。
2. 只有文字描述的人设 prompt。
3. Persona Profile。
4. Persona Profile + 检索真实 exemplar。
5. 多 donor、知识与语言分离的 persona。

比较：

* 人设盲辨度
* 内容质量
* 来源忠实度
* 跨 persona 语义重叠
* 通用 AI 结构出现率
* 人工编辑修改量

只有数据支持时才决定是否需要 LoRA。不能在没有实验的情况下把真正的风格适配全部推迟到 V2。

## 七、执行真正的知识与语言蒸馏

每个新 persona 至少组合 2–4 个互补 donor，并分别设定：

* Knowledge donor
* Reasoning donor
* Language donor
* Content habit donor
* Visual donor

系统先生成中性事实与分析对象，再由不同 persona 独立制定 Analysis Plan，最后分别写稿。

不能：

* 先生成一篇母稿
* 再换几个词
* 再翻译成另一种语言
* 然后称为多人设蒸馏

每个生成结果需要显示：

* 使用了哪些原始证据
* 使用了哪些 donor
* 从 donor 继承的是知识、分析方式还是语言特征
* 哪些标志性表达被禁止直接复制
* 为什么该 persona 适合这个题目
* 为什么其他 persona 可能选择不写

## 八、真实跨语言测试

必须至少完成两个方向：

### 中文 → 英文

选择一组中文 KOL 才较容易获得的信息、框架或市场理解：

* 提炼中性语义。
* 检查原始出处。
* 判断英文市场是否已有相同信息。
* 补充海外读者需要的背景。
* 生成自然英文内容。
* 不能只逐句翻译。

### 英文 → 中文

选择真实英文财报、机构分析或 KOL 观点：

* 提炼一手事实。
* 结合中文受众的市场和产业链背景。
* 生成中文内容。
* 保留数字、单位、hedge、归属和时间。
* 检查是否出现翻译腔和统一 AI 腔。

至少由人工对一组内容进行盲测和修改记录。

## 九、使用真实当前事件，而不是只做静态历史回放

保留 NVIDIA 历史回放作为测试夹具可以，但它不能继续担任唯一 Demo。

下一轮至少需要：

1. 一个实际正在发生或刚发生的金融事件。
2. 一个计划事件，例如即将公布的财报或宏观数据。
3. 一个从 KOL 内容中发现的主题变化。
4. 一个因新证据而需要更新旧稿的案例。

要求：

* 显示事件第一次被发现的时间。
* 显示原始来源。
* 显示后续证据如何改变内容。
* 新信息到达后，系统实际重新计算受影响对象。
* 不允许只用前端按钮切换预写好的 V1/V2 文本。

## 十、前端必须连接真实数据与模型

旧 `review-demo.html` 可保留为视觉参考，但不算工作原型。

下一版前端至少应真实连接：

* 数据库或实际本地数据集

* 清洗结果

* Persona 配置
* 真实模型生成接口
* 来源与 Evidence
* 内容版本

核心页面先只做四个，但必须真实：

### 1. Corpus / Donor Explorer

可以看到：

* 账号实际采集多少条
* 时间覆盖
* 原创/回复/转推/广告比例
* 被保留和排除的推文
* 主题聚类

### 2. Persona Lab

* 查看组合依据
* 生成 Persona Profile
* 对比不同 persona 的可辨识性

### 3. Live Content Studio

可以：

* 选择真实当前事件

* 实际调用模型生成内容
* 查看句段对应证据
* 对比不同 persona 的输出

### 4. Update / Handoff

* 显示旧稿哪些段落需要更新

## 十三、验收标准

本轮只有同时满足以下条件，才可称为 Vertical Slice：

* 至少 12 个真实 donor 被深入采集，而不是只登记名字。
* 至少约 1,800 条清洗后金融相关内容，或清晰说明真实数据不足及替换结果。
* 每条内容保留 post ID、URL 和时间。
* 有实际 Knowledge、Style 和 Habit Profile。
* 有真实 ML 分类、聚类或作者识别实验和指标。
* 有至少三个多 donor persona。
* 有同一事件下真正不同的 persona 分析。
* 有中译英和英译中真实样本。
* 有一个实际当前事件。
* 有一次真实的内容更新和版本变化。

* 点击来源可以回到真实 Evidence。
* 所有失败、数据不足和 API 限制如实记录。
* 不把模型自评分当成人工验证。
* 不把接口 200 当作蒸馏成功。

1. 已经实际采集到什么。
2. 距离目标还缺多少。
3. 需要多少请求或费用。
4. 哪个权限或输入阻挡了继续。
5. 可以立即执行的替代路径是什么。

先给出本轮实际执行计划、预计 API 调用量和预计数据量，然后开始完成上述纵向闭环。不要再次停留在 Phase 0。
